## 11. 坑 B5-E：治疗页按键导航仍比主菜单慢（2026-09-11，已修复）

### 11.1 现象
- 之前领待办：治疗页四宫格左/右键切焦点「比主菜单慢」。主菜单切焦点只是显示/隐藏一张高亮图（很快）；治疗页每切一次焦点要重读 **5 张图**（4 个格子 unSel + 1 个 Sel 图标）。
- 首轮修法：`CONFIG_LV_CACHE_DEF_SIZE=262144` + `CONFIG_LV_IMAGE_HEADER_CACHE_DEF_CNT=32`（全局图片缓存）。用户上板实测反馈「**快了一点点**」——说明缓存没真正吃到。

### 11.2 根因（LVGL 9.5 源码链追踪）
- 图片缓存启用后仍几乎无效，追 managed_components 里 LVGL 源码得出结论：
  - 四宫格图标是 **RGB565A8 / RGB565** 格式的 `.bin` 图片。
  - `lv_bin_decoder.c` 里，当 `LV_BIN_DECODER_RAM_LOAD`（默认**关**）时，RGB565/RGB565A8/RGB888 走**流式解码**分支（`get_area_cb` 按块读），`res = LV_RESULT_OK` 但 **`dsc->decoded == NULL`**。
  - `lv_image_decoder.c` 的缓存逻辑：`try_cache()`/`lv_image_decoder_add_to_cache()` **只在 `dsc->decoded != NULL` 时才往图片缓存塞**。decode 结果为空 → **永远不进图片缓存**，只有头缓存（header cache）命中。
  - 结论：`CONFIG_LV_CACHE_DEF_SIZE` 对这类图标**形同虚设**，每切一次焦点仍然整图重解码，所以只「快了一点点」。

### 11.3 修复
- `sdkconfig.defaults` 图片缓存块后新增：
  ```kconfig
  # === bin decoder RAM load (fix: image cache was bypassed for RGB565/RGB565A8) ===
  # RAM_LOAD 关闭时 RGB565/RGB565A8/RGB888 走流式解码，dsc->decoded==NULL，
  # lv_image_decoder_add_to_cache 永不被调用，上面的 LV_CACHE_DEF_SIZE 对这类图标无效。
  # 打开后整图一次性解码进 RAM(dsc->decoded!=NULL)，后续 lv_image_set_src 命中图片缓存。
  # RAM 代价 ~9KB/图 x 8 图标 ≈ 70KB，落在 8MB PSRAM，无压力。
  CONFIG_LV_BIN_DECODER_RAM_LOAD=y
  ```
- 生效流程：删根目录 `sdkconfig` → `idf.py reconfigure` → `idf.py build` → `idf.py -p COM12 app-flash`。
- 实测 sdkconfig 三开关落位：`CONFIG_LV_CACHE_DEF_SIZE=262144` / `CONFIG_LV_IMAGE_HEADER_CACHE_DEF_CNT=32` / `CONFIG_LV_BIN_DECODER_RAM_LOAD=y`。

### 11.4 结果（✅ 用户确认）

### 11.5 坑记录（沉淀）
1. **LVGL 9.5 图片缓存只对 `dsc->decoded != NULL` 的解码生效**：RGB565/RGB565A8/RGB888 在 `LV_BIN_DECODER_RAM_LOAD` 关闭时走流式解码、decode 结果为空 → 永不进图片缓存，只有 header cache 有点用。要缓存这类图标**必须开 `CONFIG_LV_BIN_DECODER_RAM_LOAD=y`**。
2. 文件源（`lv_image_set_src(filepath)`）的缓存 key 用 `strcmp` 比较路径，RAM_LOAD 开后同一路径重复 set_src 可靠命中图片缓存。
3. **烧录前先杀掉后台 monitor**：monitor 常驻占 COM12，否则 `idf.py flash` 报 `Could not open COM12, port busy`。
4. `sdkconfig.defaults` 必须保持 **纯 ASCII**（中文注释在 GBK 环境下会让 kconfgen 报错——历史已验证坑）。
